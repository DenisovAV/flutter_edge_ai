## Project Overview

**Flutter Edge AI** — multi-platform Flutter plugin for running Gemma and other on-device LLMs (Qwen, DeepSeek, Phi, FastVLM, SmolLM, …) on Android, iOS, Web, macOS, Windows, Linux. Supports multimodal vision, function calling, thinking mode, GPU acceleration, LoRA weights (MediaPipe `.task`).

## Architecture Quick Reference

### Core Principles
- **2.0 modular split** (monorepo, Dart pub workspace): core `flutter_edge_ai` owns model installation and inference/embedding/speech registries, but no engine and no RAG API. Engines/backends register through `FlutterEdgeAi.initialize(...)`. Independent `flutter_edge_ai_rag` instances own RAG orchestration and the vector-store contract; `flutter_edge_ai_qdrant` and `flutter_edge_ai_sqlite` depend on RAG and provide pluggable stores through `FlutterEdgeAiRag(providers:).open(...)`. Core never creates or disposes a `RagIndex`. The one intentional runtime-sharing edge remains `flutter_edge_ai_speech` → `flutter_edge_ai_litertlm`, because speech imports `LiteRtBindings` and consumes litertlm's native bundle.
- **`flutter_edge_ai_llama`** (opt-in): GGUF inference and native EmbeddingGemma 2 text embeddings through `LlamaEmbeddingBackend` (0.0.3), using published core 2.5.0 and llamadart 0.15.1 with Apple companion 0.15.0; use separate GGUF/LiteRT RAG vector profiles; runtime artifacts stay owned by llamadart. Its package-local `AGENTS.md` and `doc/platforms.md` describe exact pins, consumer setup and qualification gaps.
- **`flutter_edge_ai_builtin_ai`** (opt-in): OS built-in AI engine — Gemini Nano via ML Kit GenAI/AICore (Android), Apple Foundation Models (iOS/macOS), Phi Silica via Windows AI Foundry (Windows) and the Chrome Prompt API (web). Since 0.3.0 a pure-Dart adapter over the external `flutter_local_ai` package, which owns every native layer; `flutter_local_ai` never depends on flutter_edge_ai. Registers via `inferenceEngines: [BuiltInAiEngine()]`; models use `ModelFileType.builtIn` (core has no file to install — the OS owns the weights).
- **`flutter_edge_ai_onnx`** (opt-in): ONNX Runtime engines — text generation via ORT-GenAI (`OnnxEngine`) + embeddings via plain ORT (`OnnxEmbeddingBackend`), both `dart:ffi` worker-isolate. `hook/build.dart` bundles native archives for macOS arm64, linux_x64, windows_x64, windows_arm64, android_arm64 (ORT from Maven `onnxruntime-android`, genai from the `onnxruntime-genai` GitHub release), and iOS arm64 (device + Apple-Silicon sim slices from the single self-contained `onnxruntime-genai-ios` xcframework — ORT statically linked in, one binary exporting both `Oga*` and `OrtGetApiBase`, so no separate ORT and no co-location problem); `OnnxEngine.canHandle`/`OnnxEmbeddingBackend._isSupportedHost` are gated to **macOS arm64 + linux x64 + windows x64 + windows arm64 + android arm64 + iOS arm64** (in lockstep with the hook table). Windows ARM64 passed generation, embeddings, and the example build on a GitHub-hosted Windows 11 ARM64 runner (Azure Cobalt 100; 64 tokens at 10.9 tok/s, MiniLM dim 384; #326, #656). The other five arm/x64 hosts are **device-verified**: ORT-GenAI generation + embeddings run end-to-end (macOS ~54 tok/s M4 Pro, **Android ~10.4 tok/s Pixel 8 Pro FTL**, Linux ~5.3-5.8, Windows ~3.3 tok/s on the CPU test VMs; Phi-3.5-mini 3.8B int4 ≈3.74 GB peak RSS → needs a 6GB+ phone). On **iOS** the app builds, signs, installs and launches on a real iPhone, and the `@executable_path`-anchored dlopen resolves the framework + generation runs. **Co-location** (genai's bare-name `dlopen("libonnxruntime")` resolving to the sibling CodeAsset): macOS+Linux via the `ORT_LIB_PATH`/`dladdr` export in `gen_ai_client.dart` (`_exportOrtLibPath`, mac/linux only), **Windows + Android resolve on their own** (genai's self-directory dlopen finds the co-located lib under Flutter's flat CodeAsset layout), **iOS has no second lib** (ORT static in genai; the Dart loader opens the one framework via the `@executable_path/Frameworks/…framework/…` anchor iOS dyld 4 requires — bare `.framework` names don't resolve). `OnnxEngine.canHandle` declines + logs off-host; `OnnxEmbeddingBackend.canHandle` stays extension-based on every platform (so LiteRT's catch-all can't silently claim an `.onnx` file) and gates in `describe()` instead. ORT-GenAI model installs are a DIRECTORY (`genai_config.json` + `.onnx`[+`.onnx_data`] + tokenizer) — `installModel(…).fromHuggingFace(repo)` installs the whole directory (the ONNX resolver carried by `OnnxEngine` picks a CPU execution-provider folder).
- **`flutter_edge_ai_diagnostics`** (opt-in, contributed in #541 and #600 for #517): `MemorySnapshot(anonymousBytes, availableBytes, fileBackedBytes, anonymousPeakBytes, takenAt)` read from the OS — Android and Linux `Private_Dirty + SwapPss` (`/proc/self/smaps_rollup`) + `MemAvailable`, and `fileBackedBytes` = `Private_Clean + Shared_Clean`: resident clean pages (mapped files on a CPU backend, but also GPU driver buffers on Adreno: the `/dev/kgsl-3d0` mapping is ~88% clean: one Gemma 4 E2B GPU run added ~980 MiB there on the vivo, ~115 MiB of it dirty and so in `anonymousBytes`; all file mappings together were ~260 MiB; Mali not measured) and clean anonymous pages (zram readback, `MADV_FREE`), so a before/after delta is not an exact count of model weights; iOS and macOS `phys_footprint` (`task_info(TASK_VM_INFO)`, offset 144 / REV1 count 38) + `anonymousPeakBytes` = `ledger_phys_footprint_peak` (offset 168, needs a reply of 44 natural_t; null when shorter, null on Android and Linux; a lifetime mark, never reset) + iOS `os_proc_available_memory()` (null on macOS, which has no per-app limit), `fileBackedBytes` null (not read yet; `TASK_VM_INFO.external` is the follow-up). Pure `dart:io`/`dart:ffi`, no native code, **no dependency on core** (it measures the process, whichever engine runs in it). Android + iOS + macOS + Linux (0.5.0: the same two `/proc/self/smaps_rollup` fields and `MemAvailable` as Android, machine-wide and ignoring a cgroup `memory.max`; GPU memory in neither field, an iGPU still uses system RAM; `gpuMemory()` returns null there; an AppArmor refusal stays `MemoryReadException`); elsewhere `memorySnapshot()` throws `UnsupportedError`. Experimental `FlutterEdgeAiDiagnostics.gpuMemory()` → `GpuMemoryReading` (0.4.0; a separate call, not a snapshot field: `inAnonymousBytes` = kgsl `Private_Dirty`, `inFileBackedBytes` = kgsl `Private_Clean + Shared_Clean`, each already in the snapshot field it names; `outsideSnapshotBytes` always null; null = no `/dev/kgsl-3d0` on the device (tested with `existsSync`; an Adreno process that maps nothing yet gets zeros); read from `/proc/self/smaps` as Latin-1, `kgsl-3d0` matched anywhere in the name, malformed or missing input throws). A null field = the value is not reported on this platform/OS version; a failed read throws `MemoryReadException` — never collapse the two. Android GPU memory (KGSL/Mali/dmabuf) is mostly outside `anonymousBytes`; on Adreno most of it is counted in `fileBackedBytes` instead (clean pages of the `/dev/kgsl-3d0` mapping).
- **Probe-chain registry**: `EngineRegistry`/`EmbeddingRegistry` select a provider by `canHandle(spec)` + `priority` (descending priority, ascending registration index). Engines are pure factories; core owns singleton lifecycle via `CloseNotifier`/`addCloseListener`.
- **ModelSource**: Type-safe sealed class (`NetworkSource`, `AssetSource`, `BundledSource`, `FileSource`). See `packages/flutter_edge_ai/lib/src/domain/`
- **Install vs Runtime separation**: Installation stores identity (modelType + fileType), runtime accepts config (maxTokens, backend, etc.) via `RuntimeConfig`
- **Engine selection by declared `ModelFileType`** (via `canHandle(spec)` — NOT by sniffing the file name): `task`/`binary` → MediaPipe, `litertlm` → LiteRT-LM, `builtIn` → BuiltInAi, `onnx` → OnnxEngine, `gguf` → the opt-in llama.cpp engine (`flutter_edge_ai_llama`; core treats its chat template as the file's own and cleans replies as for `binary`). `installModel` defaults `fileType` to `task`, so `.litertlm` must be declared explicitly or it is routed to MediaPipe
- **All five platforms (Android/iOS/macOS/Linux/Windows)**: Dart → `dart:ffi` → LiteRT-LM C API for inference and LiteRT C API for embeddings, both implemented in `flutter_edge_ai_litertlm`. `flutter_edge_ai_embeddings` contains tokenizer implementations only; it owns no native backend or bundle. Native prebuilts are fetched at build time from GitHub release `native-v0.18.0-h` (Native Assets). `flutter_edge_ai_litertlm/hook/build.dart` is the **sole** hook carrying the LiteRT native version; `flutter_edge_ai_speech` has no hook of its own and consumes the bundle through its direct litertlm dependency. The cycle-fix `stage()` in the hooks is **Apple-only** (Xcode `directoryTreeSignature` cycle; staging on Windows splits companion DLLs and hangs cancel/close).

## SDK Gotchas (Non-Obvious)

### ⚠️ maxTokens = CONTEXT window, not output length (#318)
`maxTokens` (on `getActiveModel`/`createModel`) is the whole **context window** — input (system + history + message) **plus** generated output, i.e. the KV-cache budget. It is **NOT** the response length. CPU/GPU `.litertlm` bundles bake a `kv_cache_max_len` (1024 for the supported bundles — Gemma 4 E2B, FunctionGemma, …); a `maxTokens` below it underflows the native magic-number KV-cache resize and `DYNAMIC_UPDATE_SLICE` fails to allocate tensors at generation (cryptic `Stream error: INTERNAL: …executor.cc:734`). Verified on Pixel 8a (CPU): 100/256/512 crash, 1024/4096 work.
- The litertlm engine **clamps `maxTokens` up to 1024 for CPU/GPU attempts** with an `edgeAiLog` warning (`clampLitertlmContextTokens` in `flutter_edge_ai_litertlm/lib/src/litert_lm_engine.dart`). It deliberately does **not** clamp `PreferredBackend.npu`: an NPU bundle has one compiled `cache_length`, which can be below 1024 (896 is the largest that keeps every prefill chunk in a Gemma 3 `npu_export` build for Qualcomm at prefill 128, LiteRT-LM#3508), and the 1024 floor is a CPU/GPU fact. Raising 896 to 1024 would not break such a bundle: LiteRT-LM's NPU executor lowers a larger `max_num_tokens` to the compiled limit of a bundle with a static KV cache, with a warning (v0.18.0 source, `DetermineMaxSequenceLengthStaticModel`; not run on a device). The caller must use that bundle's required context size. A bundle compiled for an NPU never runs on GPU/CPU, and a generic one is never tried on the NPU (it has no NPU graph: LiteRT-LM would run it on the CPU and report `npu`, measured on a DDP Galaxy S24 2026-10-18), so the clamp applies to every GPU/CPU attempt. MediaPipe `.task` also is not clamped.
- To cap **generation length**, use the new **`maxOutputTokens`** on `createSession`/`openSession` → native `set_max_output_tokens` (litertlm only; MediaPipe has no session-level output cap and logs that it's ignored).
```dart
// ❌ WRONG - meant "100-token reply", actually shrinks the context → crash on .litertlm
await FlutterEdgeAi.getActiveModel(maxTokens: 100);
// ✅ CORRECT - context stays 1024+, output is capped at 100
final model = await FlutterEdgeAi.getActiveModel(maxTokens: 1024);
final session = await model.createSession(maxOutputTokens: 100);
```

### ⚠️ Unset sampling is the model's own, not greedy (#572)
`temperature`, `topK`, `topP` and `randomSeed` on `createSession`/`openSession`/`createChat`/`openChat` are nullable (core 2.2.0). An unset one resolves, field by field, in `SamplingParams.resolve`: the model file's sampler (native `.litertlm`: read in Dart from the container header and its `LlmMetadata` section, `litertlm_bundle_sampler.dart` — NOT LiteRT-LM's `litert_lm_loaded_file_create`, which copies vision sections and, without `max_num_tokens`, the whole main graph into the heap: 1 GB for Gemma 4 E2B; ONNX `genai_config.json`) → `SamplingParams.forModelType` (publishers' `generation_config.json` values) → `SamplingParams.fallback` (0.8 / 40 / 0.95 / seed 1). `topK: 1` or `temperature: 0` is greedy (`isGreedy`); a caller who sets a temperature or topP but no topK skips greedy layers (`needsSamplingTopK`), and invalid values throw `ArgumentError`. A failed bundle read is not the same as "no sampler": it sets `LiteRtLmFfiClient.bundleSamplerError` and prints once. Native `.litertlm` always sends a resolved TOP_P sampler: a config without one makes LiteRT-LM copy the bundle's sampler whole, and its CPU sampler rejects TOP_K/GREEDY. Web `.litertlm` cannot read the bundle, so it uses the family defaults, and must send `type: 2` or the engine discards the values. MediaPipe holds an unset topK to 40, its own default top-k. `LlmInferenceOptions.maxTopK`, which the plugin leaves at 40, is not a ceiling: on Android CPU and GPU (Mali, Adreno) an explicit topK 64 samples beyond the top 40 (FTL 2026-10-11); iOS and web are not measured. A temperature of 0 is sent to MediaPipe as 1.0 with topK 1: it picks greedy from top-k alone, its CPU sampler treats temperature 0 as 1.0, and its GPU sampler divides by it. Built-in AI sends `flutter_local_ai`'s own 0.8 / topK 1 for unset values: it takes no null, and a larger topK could exceed a browser's `maxTopK`. Still true: the sampler is fixed by the engine's first generation (LiteRT-LM#2080) — `EngineSamplerLatch` records it at the first send (native client and web model) and prints a one-time warning when a later session asks for other values and the caller set either side — its random state carries across conversations, and NPU decodes greedily whatever is sent. Measured 2026-10-10 on macOS CPU: Gemma 4 E2B and FunctionGemma 270M tool calls and Gemma 4 JSON are equally accurate under the family defaults and greedy, at the same speed.

| `native/litert_lm/{build_ios.sh,patch_c_api.sh,stream_proxy.c}` | iOS dylib rebuild + C API patcher + preload helper; `stream_proxy.c` exports `stream_proxy_create2` (in every archive since `native-v0.18.0-f`, required by the Dart client since litertlm 1.15.0): the client resolves the three v0.15 chunk accessors on the library it drives and passes them in, the shim keeps no global state; `stream_proxy_create`, the ambient probe older Dart used, stays in the source until the next native tag; host test `stream_proxy_test.c` + `fake_litert_lm.c` (ThreadSanitizer, commands in its header). `patch_c_api.sh` §16 (`patches/conversation_rewind_cancelled_turn.patch`, in every archive since `native-v0.18.0-f`) adds `litert_lm_conversation_rewind_cancelled_turn(conv, messages_json, extra_context, optional_args, out_last_turn_end)`: each send saves a checkpoint right before its own prefill and the C wrapper records how each send ended (completed / cancelled / failed, numbered per send); the call cancels whatever still runs, waits until every task of the session has ended (`Conversation::WaitUntilDone`, backported from upstream main), and only then decides — completed: 0, nothing changes; cancelled: rewind to the checkpoint (restoring the task dependencies the cancel poisoned) and prefill the stopped exchange without decoding; anything else: non-zero, delete the conversation. Deciding before the wait read a cancel that had not landed yet as "not cancelled" and left a chat silent (#682 review). `RecoveringConversationHandle` calls it on a spawned isolate and rebuilds from text on the NPU (one-token rollback only), on a library without the export, or with a printed warning when it fails; `verify_tarball_manifest.sh` refuses a tarball whose libLiteRtLm lacks the export |
